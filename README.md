# Лабораторная работа № 1 - LangChain, Structured Output, SQLite и обработка ошибок

Небольшой учебный проект на **LangChain (LCEL)**: от простой цепочки `Prompt → LLM → Parser` до структурированного вывода через Pydantic, интеграции с SQLite, повторных попыток (retry) и диалогов с сохранением состояния.

## Что внутри

Ноутбук `lab01.ipynb` состоит из пяти частей:

1. **Базовая цепочка LangChain** — `ChatPromptTemplate`, LCEL-цепочка `prompt | model | StrOutputParser()`, сравнение `invoke()` и `batch()`.
2. **Structured Output и Pydantic** — описание схемы `ProductQuery` (категория, максимальная цена, сортировка), `PydanticOutputParser`, сравнение режимов **thinking on/off** по времени и токенам.
3. **Вызов классического ПО (SQLite)** — создание и заполнение базы `products.db`, параметризованный SQL-поиск, объединение LLM и БД через `RunnableLambda`, оформление поиска как инструмента (`@tool`).
4. **Retry и журнал выполнения** — перехват `OutputParserException`, `with_retry()`, сравнение поведения с повторными попытками и без них.
5. **Уточняющие запросы** — цепочка с передачей текущих параметров поиска, сравнение полной истории диалога и хранения состояния (в т.ч. по расходу входных токенов).

- VS Code с расширениями Python и Jupyter либо Jupyter Notebook;

## Запуск

1. Откройте `lab01.ipynb` в VS Code или Jupyter.
2. Выберите kernel, в котором установлены зависимости.
3. Убедитесь, что включён университетский VPN (или вы в сети университета).
4. Выполняйте ячейки **последовательно сверху вниз**.
5. При запросе введите API-токен в ячейке настройки окружения.
6. Дождитесь успешного тестового запроса к модели и продолжайте выполнение частей 1–5.

> Для проверок в части 4 (retry) используется `FakeListChatModel` — доступ к серверу модели там не требуется.

## Важно: база данных `products.db`

Файл базы создаётся автоматически при запуске ноутбука — отдельно прикладывать его не нужно.

**Не запускайте повторно ячейки создания и заполнения БД, если `products.db` уже существует и заполнен.** В ноутбуке используется `CREATE TABLE IF NOT EXISTS`, после чего выполняется `INSERT` тестового списка товаров. Повторный запуск ячейки заполнения добавит те же записи ещё раз — в таблице появятся дубликаты (ограничений уникальности для товаров нет).

Как поступать:

- **Первый запуск в новой папке:** выполните ячейку создания таблицы и ячейку добавления товаров по одному разу.
- **Повторный запуск с уже созданным `products.db`:** пропустите обе ячейки и переходите к проверке содержимого и следующим этапам.
- **Перезапуск ядра Jupyter** сам по себе файл БД не удаляет — SQLite-файл сохраняется на диске.
- **Сброс базы:** закройте соединение с БД, удалите `products.db` из папки проекта и выполните ячейки создания и заполнения один раз.

Файл `products.db` появляется в рабочей папке после первого запуска соответствующих ячеек.

## Основные выводы работы

- Прямой вызов `model.invoke()` возвращает `AIMessage`, а цепочка с `StrOutputParser()` - строку; `batch()` обрабатывает несколько запросов за раз.
- Схема Pydantic гарантирует корректность **структуры** данных, но не **смысловую** точность извлечённых параметров.
- Включение режима thinking заметно увеличивает число выходных токенов и время ответа, но не всегда улучшает интерпретацию неоднозначных запросов.
- Аргументы инструмента (tool calls) необходимо валидировать через Pydantic до обращения к базе.
- `with_retry()` позволяет автоматически повторять попытки при `OutputParserException`; после исчерпания попыток ошибка возвращается вызывающему коду.
- Хранение текущего состояния диалога сохраняет корректность параметров и снижает расход входных токенов по сравнению с передачей полной истории (в экспериментах - около 8%).

## Примечания

- Токен API вводится вручную при запуске и не хранится в репозитории.
